Quadrotor flight software, written from scratch

A complete guidance, navigation and control stack for a 7-inch quadrotor, with no flight-control libraries. Every algorithm is designed and validated in MATLAB first, then ported one-to-one to C++ and verified again with unit tests that run on a laptop, so most bugs are caught before they reach hardware.

Where it stands: estimation, control and the flight state machine are ported and tested, and all four sensors are running on the bench. The airframe is not yet integrated and the vehicle has not flown. Remaining before first hover: flight-core integration, closed-loop simulation, the ESC driver and logging.

Architecture

Flight logic never touches hardware. Drivers sit behind one interface, and everything downstream takes plain data in and returns plain data out, which is what makes the whole stack testable without the vehicle.

Sensor driversIMU, magnetometer, barometer, GNSShealth + freshness flags
State estimatorMadgwick (primary), complementary (seed, fallback)3-state vertical Kalman filter
Controllerangle PID → rate PID per axisaltitude PID on hover thrust
Motor mixerquad-X allocationshift-then-scale saturation handling
Flight state machineboot checks, arming, takeoff, landing, failsafes · pure logic, 35 tests
  • Two attitude filters, one authoritative. A complementary filter seeds Madgwick at boot and keeps running. If Madgwick goes numerically unstable, the estimator falls back to it and the state machine starts a level descent.
  • Health and freshness are separate signals. "Is this sensor trustworthy" and "is this a new sample this tick" are tracked independently, so a slow but healthy sensor is never treated as a fault and a held reading is never fused twice.
  • Failsafes are recomputed every tick. The active failsafe is always the highest-priority condition currently tripped, so escalation and recovery need no special-case code.
  • Tests are checked against broken code. Each new suite is validated by deliberately removing a condition or a latch and confirming a test fails.

A bug that only existed on real hardware

The sensor health checks passed every host-side test, then raised false alarms as soon as they ran on the board. It turned out to be three separate problems stacked on top of each other:

  1. Rate mismatch. The GNSS reports at 10 Hz and the loop runs much faster, so most ticks have no new message. The health logic read that as the sensor going quiet.
  2. Cold start. A receiver that is still acquiring its first fix is working correctly, but it was being counted as failing. It now gets a one-time grace window, and "has a fix" is reported separately from "is healthy".
  3. A race in the receiver library. Reading the "new data" flag could consume it, so freshness was unreliable. Freshness is now taken from the message's own GNSS time-of-week advancing, which reading cannot consume.

The fix became the design: every driver now reports health and freshness as two separate things, and the estimator only fuses a sample that is both.

Fixed-wing UAV: telemetry lead to project lead

I joined in October 2025 and took ownership of the communications subsystem end to end: choosing the radio hardware with the structures team, then building the software up to a full MAVLink link with QGroundControl. For the 2026–27 year I lead the fixed-wing project as a whole.

900 MHzair-to-ground MAVLink link on an RFD900x pair
25 msone-way latency at 200 kbps
1–2 kmrange the link has been field-tested at
  • Two-way control over the radio. Radio-controller inputs are forwarded by QGroundControl over the backlink and drive the roll, pitch and yaw servos, with telemetry coming back the other way. This was the minimum viable product I presented at the critical design review.
  • Requirements first. At the preliminary design review I helped set the size and scope of the link, which is what produced usable antenna requirements.
  • Lightweight telemetry logger. A FreeRTOS task writes sensor data in binary to a file, with a Python decoder on the host. It is a working skeleton, not yet a full analysis tool.
  • Project lead. I set milestones and priorities, run design reviews, write onboarding material for new members and coordinate with the structures team. Guidance and navigation work on the airframe starts later this year.

Snake on an FPGA

The classic game in digital logic, played with an NES controller on a 16×16 LED matrix. The design is split into separate modules for the snake, apple, collision detection, game state, input and display, each with its own testbench.

I deliberately stored the snake as an array of coordinates, the way software would, to see what it costs in hardware. It costs a lot: the array has to be unrolled into logic, which capped the snake at 64 segments. That was the most useful lesson of the project.

  • Wrote the NES controller driver and synchronised its inputs into the game clock domain.
  • Debugged cases where simulation and synthesised hardware disagreed.
  • Block diagrams, state machines and per-module decisions are in the full report.
